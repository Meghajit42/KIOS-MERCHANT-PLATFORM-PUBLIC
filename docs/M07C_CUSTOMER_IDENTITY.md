# M07C internal customer identity foundation

Development only. `KIOS_CUSTOMER_IDENTITY_ENABLED` defaults off and requires APP_ENV=demo. There is no public route, registration, login, verification-code transport or token issuer. Existing merchant API and session behavior is unchanged. Customer operations are not exposed through merchant APIs.

## Domain and authority

Customer UUIDs identify platform accounts, independently of merchant/outlet UUIDs and native staff accounts. Customer records have no merchant-role, outlet-membership or staff-permission relationship. Future order ownership will reference a customer UUID and separately authorized merchant/outlet/order scope; a shared customer account must not permit cross-merchant order inspection. Delivery identity is a separate future domain and is not implemented.

Only an existing native platform administrator may provision a synthetic account or apply lifecycle transitions. Merchant owners and restaurant staff are not platform administrators. The existing MerchantProvisioner transaction port rechecks platform authority under locks. The service has no administrator profile-listing/export operation.

Customer-owned profile and consent operations accept the separate CustomerIdentityProvider port, not the merchant AuthenticatedUserProvider. This is a trusted server integration boundary, not an authentication implementation. No concrete customer provider is bound to HTTP or instantiated by the application. Synthetic providers exist only in qualification tests. A future provider must derive identity from a verified server-owned customer session, never from submitted IDs, merchant cookies or unsigned tokens. Merely implementing this interface is not proof of authentication. No future deployment may wire a request-controlled provider into this service.

## Data and lifecycle

Migration 036 adds customer_accounts, customer_consents and customer_security_events. Existing merchant tables are untouched. Synthetic normalized handles are case-insensitive through lowercase/trim normalization and a database unique key; raw email/phone/address fields are deliberately absent. Names and handles accept only clearly synthetic values. Stable UUIDs are generated by the established UUID utility. Contacts remain explicitly UNVERIFIED with no setter or delivery integration; this is not a claim of verified email/phone support.

States: PENDING may become ACTIVE or DEACTIVATED; ACTIVE may become SUSPENDED or DEACTIVATED; SUSPENDED may become ACTIVE or DEACTIVATED; DEACTIVATED is terminal. Lifecycle control is platform-only. Active customers may change only their synthetic display label or append an explicit consent decision, not their handle, verification, state, roles or ownership. Suspended accounts can read their own minimal status/profile but cannot edit or consent. Deactivated accounts deny retained customer authority. No account is silently deleted; consent and audit history are preserved. No automatic consent grants or cascading merchant permissions are added.

Account versions and FOR UPDATE locks serialize concurrent modifications; stale expected versions fail. Native admin checks and customer ownership checks are repeated inside transactions. Every mutation inserts a security event with actor domain, server-owned actor ID, target ID, operation/version and UTC epoch, with no profile/contact/secret payload. Consent has explicit purpose (terms/privacy/marketing), policy version, grant/withdrawal, account version and UTC epoch. Both histories reject UPDATE/DELETE. Audit insertion failure rolls back account and consent changes atomically. Client-visible projections omit creation timestamps and audit metadata; no password, cookie or secret is returned.

## Credentials and recovery design boundary

No customer password or publicly usable token is stored or issued in Shift 01. Existing merchant credential handling is reused unchanged. Future separately authorized customer authentication must use the established StaffPasswords hashing/verification policy (PHP password_hash/password_verify with supported policy and rehashing), a dedicated customer credential table and revocable customer session domain. Never reuse merchant credential rows or treat the synthetic handle as an authenticator.

Account recovery is design-only: require an explicitly verified contact or approved attended recovery proof; use server-generated one-time high-entropy proofs stored only as hashes, bounded expiry/attempts, single atomic consumption, session revocation, generic enumeration-safe errors and immutable recovery audits. No recovery proof, privileged override, password reset or contact-verification bypass is implemented. Recovery must not implicitly reactivate a deactivated account. Actual recovery/contact proof and public authentication need specialist qualification before integration.

## Future application contracts

Trusted customer provider -> own profile/consent service -> minimal account projection. Future customer catalogue/discovery adapter must define its own audience and reuse safe native reads without borrowing merchant permissions. Future customer order history/delivery tracking requires explicit customer-owned order associations and a separate delivery authorization model. These flows are not implemented or activated here. Public ordering remains closed; public registration/authentication, real payments and delivery dispatch disabled.

## Qualification

Use only the established hardened guest, synthetic identities and disposable MariaDB. Exercise normalization/duplicates, lifecycle/version conflicts, ownership/type separation, platform privilege rejection, real competing version updates, immutable histories, audit-failure rollback, referential integrity and prior merchant regression. The trusted provider interface itself cannot prevent malicious code already executing inside the trusted PHP process; integration must enforce the documented provenance boundary. No public security claim follows from an internal service test.
